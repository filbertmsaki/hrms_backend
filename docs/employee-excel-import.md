# Employee Excel Import Module

## Analysis Summary

### Existing employee creation flow

- Employee creation is centered in `EmployeesService.create()`.
- The service validates branch, department, position, reporting line, contacts, and onboarding inputs.
- Employee numbers are reused when provided and generated by the existing service when omitted.
- Leave balances and onboarding setup are triggered by existing business rules after employee creation.

### Existing user and company linkage

- The current schema requires `employees.company_user_id`.
- Every employee must be linked to a `company_users` membership and therefore to a `users` record.
- Because of that constraint, the import module keeps backward compatibility by creating an inactive placeholder user and company membership when `create_system_user` is effectively disabled.

### Existing org and attendance relationships

- Branches, departments, and positions are company-owned records.
- Employees can be linked to managers through `reports_to`.
- Shift assignments and timetable assignments already exist as separate operational services and are reused after import.
- Attendance devices, employee device assignments, and employee access credentials are separate access-control records and are not collapsed into the employee table.

### Existing access-control relationships

- Device employee numbers are handled through employee-device assignment and credential records, not by assuming they equal HRMS employee numbers.
- Import reuses those tables and prevents duplicate device employee numbers on the same device.
- Device-side synchronization is treated separately from database import completion so offline hardware does not block HRMS employee creation.

## Implemented Backend Endpoints

- `GET /employees/import/template`
- `POST /employees/import`
- `POST /employees/import/preview`
- `POST /employees/import/confirm`
- `GET /employees/import/history`
- `GET /employees/import/:batchId/result`

All routes are authenticated and permission-protected.

## Permissions

- `employees.import.template.download`
- `employees.import.preview`
- `employees.import.execute`
- `employees.import.history.view`
- `employees.import.result.download`

These permissions were added to seed data and assigned to company roles:

- `COMPANY_ADMIN`: full import access
- `HR_MANAGER`: full import access
- `HR_OFFICER`: full import access
- `AUDITOR`: history and result download access

## Import Modes

- `CREATE_ONLY`
- `UPDATE_EXISTING`
- `CREATE_OR_UPDATE`

The frontend currently defaults to `CREATE_OR_UPDATE` because the existing service already supports safe matching and partial reuse of existing employee records. If stricter rollout is required, the UI default can be switched to `CREATE_ONLY` without schema changes.

## Accepted Values and Formats

- Dates: ISO `YYYY-MM-DD`
- Boolean values: `true` or `false`
- Gender: current employee service-compatible values only
- Employment status: current `EmploymentStatusEnum`
- Employment type: current `EmploymentTypeEnum`
- Multi-device values: comma-separated device codes
- Lookups: branch, department, position, shift, timetable, device, and role codes or IDs

## Matching and Duplicate Rules

Rows are matched against existing employees using available unique identifiers:

- employee number
- email
- phone number
- national ID

The import also validates conflicts for:

- duplicate spreadsheet headers
- missing required columns
- duplicate employee numbers within the file
- duplicate device employee numbers within the file
- invalid branch, department, position, shift, timetable, role, and device references
- invalid manager references

Blank optional cells are ignored during updates and do not clear existing values.

## Preview and Confirm Flow

### Preview

Preview parses the workbook, validates rows, stores a temporary import batch, and returns:

- row counts
- valid and invalid totals
- duplicate totals
- validation summary
- row-level errors and warnings

### Confirm

Confirm requires the preview token from the validated batch.

- Stored raw rows are revalidated server-side.
- Import status is written into batch and row history tables.
- Result workbooks can be downloaded afterward.

## Import History

Two new tables support auditing:

- `employee_import_batches`
- `employee_import_rows`

Captured data includes:

- batch ID
- original file name
- file size
- import mode
- row totals
- success and failure counts
- warning counts
- created and updated employee counters
- created user counters
- device assignment counters
- import timing
- row-level status, warnings, and errors

## Result Workbook

`GET /employees/import/:batchId/result` exports:

- original row data
- import status
- action taken
- employee and user IDs where created or matched
- row-level errors
- row-level warnings

Potentially dangerous spreadsheet values are prefixed during export to reduce formula injection risk.

## Compatibility Notes

- The existing HRMS schema does not currently support a truly user-less employee record because `company_user_id` is mandatory.
- Access-control synchronization is persisted as database state first and may remain pending when physical devices are unavailable.
- The current implementation reuses employee creation logic where practical but keeps import orchestration, preview storage, and result reporting in the dedicated import service.
