# Attendance phase 1: secure device credentials and verify the baseline

These steps require an operator with access to the intended environment and a test device. Run commands from the backend directory with the same environment and database configuration used by the application. Do not paste secrets into tickets, logs, or screenshots.

1. Inventory the backend, frontend, PostgreSQL, Redis, queue workers and scheduled jobs. Record application versions, device model and firmware, time zone and ISAPI capabilities. Confirm the intended database before making changes.
2. The application uses its existing application secret automatically: the optional existing device-specific secret takes precedence, followed by `APP_KEY`, `JWT_SECRET`, then `JWT_ACCESS_SECRET`. No new environment variable is required. All backend instances and commands must use the same selected secret. Back it up securely; changing or losing it makes encrypted device passwords unreadable. Production requires an existing application secret and does not use the development fallback. Do not remove a device-specific secret if existing ciphertext was encrypted with it.
3. Take and verify a database backup and restrict access to existing backups: old backups can contain plaintext device passwords. Deploy the compatible backend and frontend to a test environment first. At startup the backend verifies existing ciphertext and encrypts eligible legacy plaintext values in a transaction. Blank passwords and those with surrounding whitespace are skipped and logged for manual rotation.
4. Run `npm run attendance:device-secrets` for a read-only count and confirm the plaintext count is zero after startup. It also verifies that encrypted values can be decrypted. An operator can use `npm run attendance:device-secrets -- --apply` for a manual backfill; the command aborts on values with surrounding whitespace. Resolve any skipped values by rotating those device passwords.
5. In an authenticated device list, detail, create and update response, verify `api_password` is absent. Confirm that an edit with the password left blank retains the current password, and a replacement password works. Confirm browser form drafts contain no password. Existing browser drafts from earlier versions can contain old passwords; clear them on shared workstations.
6. Using an approved test device, test connection, user import, group sync and a date-range attendance pull. Record per-item results and failures without recording passwords, PINs, cards or biometric templates. Confirm processing workers and scheduled jobs are running and inspect unmatched logs, exceptions and failed jobs.
7. Rotate device credentials that may have been exposed through prior API responses, browser drafts, logs or backups. Update them in the device and HRMS; verify the connection afterward. Review retention and permissions for old audit logs and backups.

The encryption backfill does not rotate credentials or remove secrets from historical backups and logs. The phase is not complete until the live checks and rotation have been performed and documented. This runbook does not establish continuous online monitoring; that belongs to phase 2.
