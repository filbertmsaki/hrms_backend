# Unified access control: phase 0 rollout and verification

Phase 0 keeps existing device and attendance workflows while protecting PINs, narrowing removal defaults and correcting device import actions. Do not execute this procedure against production devices or data until the implementation plan is approved.

1. Record deployed backend/frontend versions, database and Redis/worker health, scheduled job status, device models and firmware, and current failed/unmatched records. Confirm all application instances use the same stable existing application encryption secret. Restrict access to logs and backups and verify a recoverable database backup.
2. In a test environment, stop or drain all old backend instances and workers. Apply migration `1797900039000-EncryptEmployeeAccessPins` before starting this version: it widens `employee_access_credentials.pin_password` to text. Old application versions cannot safely interpret encrypted values; do not run old and new writers together after the backfill.
3. Deploy the matching backend and frontend, then run `npm run access:employee-pin-secrets` from the backend directory to check the key and count existing PINs. The command is dry-run by default and does not print PINs. Resolve any error; blank or whitespace-sensitive PINs must be rotated manually.
4. When explicitly approved, run `npm run access:employee-pin-secrets -- --apply`, then run the dry run again and verify the plaintext count is zero. The conversion is transactional. Newly written PINs are encrypted by the entity transformer; legacy plaintext remains readable until backfilled. Do not rotate or change the selected encryption secret without a separate re-encryption procedure.
5. Verify device registration, connection testing, group preview, group sync readiness and attendance collection with an approved test device. Confirm user and fingerprint imports call the manage action and show a queue job rather than reporting completion immediately. Verify completed, partial and failed results through the sync logs/job API.
6. Open employee removal from a group and a device. Confirm only the explicitly selected group or device is preselected, and that archive, shift ending and fingerprint disabling are off by default. Confirm the summary and permissions before any test action. Group membership removal alone does not guarantee device revocation; effective-rights reconciliation is a later phase.
7. Confirm device API passwords, employee PINs and raw user response secrets are not exposed in API responses or stored browser drafts. Historical logs, device response metadata and backups may already contain secrets; review access, retention and rotate exposed device credentials and employee PINs according to policy.
8. Verify migration rollback on a test copy. The down migration deliberately refuses to shrink the column while encrypted or oversized PINs exist. A rollback to an old application requires a separately approved recovery or PIN rotation plan; never simply remove the key or truncate ciphertext. Restore from the verified backup if necessary, accounting for writes after that backup.

Live hardware, production permissions, deployments, backfill and rotation are not completed by the source changes or unit tests.
