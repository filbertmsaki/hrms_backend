# Effective rights: phase 1 progress

The current implementation provides a read-only, company-scoped calculation of the active group grants for one employee and device. The access group screen can compare current group-derived rights with the result of removing the current group. The API requires authentication, tenant scope, `access_groups:read`, access to the employee and the device's branch. Devices without a branch require company-wide scope:

`GET /api/access-control/employees/:employeeId/devices/:deviceId/effective-access`

Add `?exclude_group_id=<id>` to simulate removal of an active membership. The calculation deduplicates identical door/template grants, lists the groups granting each right, and reports conflicting templates on the same door. `desired_version` is a stable hash of the calculated door/template set. Recorded HRMS rights are supplied for context only; the actual device is not queried and the result does not authorize or execute changes. The preview can become stale if configuration changes.

Group employee additions and removals now atomically create a `PENDING_REVIEW` record per linked device. A company-scoped administrator can view the latest records from the group screen or `GET /api/access-control/reconciliation-operations`. An authorized administrator can explicitly request a read-only device user lookup with `GET /api/access-control/reconciliation-operations/:id/inspect-device`; it reports group-derived desired rights and device-reported rights, without changing the record or device. These records are not dispatched, retried or applied to devices; they are not proof of revocation. Group removals made by other paths, such as organization and offboarding operations, are not yet recorded by this mechanism.

The existing group synchronization guard remains in place. This phase is not complete and no automatic revocation or combined-rights device push has been added. Before enabling those operations, implement coverage of all membership and configuration change paths, durable workers, revision checks, idempotency, retry/backoff and operator visibility; define ownership of manually configured device rights; read the actual device state, preserve unmanaged rights, write one complete effective state, and verify it by reading back. Cover offline failures, concurrent membership changes, same-door conflicts and remaining group access with integration and representative hardware tests. Coordinate with the existing offboarding pipeline rather than replacing it.

The new operation table requires migration `1797900040000-CreateAccessReconciliationOperations`; the code must not be deployed without the migration. The down migration refuses to delete recorded operations. Back up first, coordinate older writers and verify the earlier phase 0 PIN migration separately. The migration has not been run and no device calls have been made. Records do not establish that PINs, cards, fingerprints, credentials, or door rights are present on the device.
