# Effective rights: phase 1 progress

The current implementation provides a read-only, company-scoped calculation of the active group grants for one employee and device. The access group screen can compare current group-derived rights with the result of removing the current group. The API requires authentication, tenant scope, `access_groups:read`, access to the employee and the device's branch. Devices without a branch require company-wide scope:

`GET /api/access-control/employees/:employeeId/devices/:deviceId/effective-access`

Add `?exclude_group_id=<id>` to simulate removal of an active membership. The calculation deduplicates identical door/template grants, lists the groups granting each right, and reports conflicting templates on the same door. `desired_version` is a stable hash of the calculated door/template set. Recorded HRMS rights are supplied for context only; the actual device is not queried and the result does not authorize or execute changes. The preview can become stale if configuration changes.

Group employee additions and removals create a `PENDING_REVIEW` record per linked device. A company-scoped administrator can view the latest records from the group screen or `GET /api/access-control/reconciliation-operations`. An authorized administrator can explicitly request a read-only device user lookup with `GET /api/access-control/reconciliation-operations/:id/inspect-device`; it reports group-derived desired rights and device-reported rights, without changing the record or device. Unlinked device users retain their device employee number for review and cannot be inspected until linked to an HR employee. These records are not dispatched, retried or applied to devices; they are not proof of revocation.

Change capture covers explicit group-device and group-door changes, group status and removal, organization removal, offboarding, onboarding, employee assignment and status changes, schedule edits and imports, direct employee/device assignments and rights, credentials, and device-imported group memberships. Two migrations extend records to include direct targets, unlinked device employee numbers and effective dates, and add database triggers. Credential values are never stored in the reconciliation records. The existing organization-removal and offboarding paths can still perform device operations; these records do not replace those behaviors. Confirm that the migrations are applied and the deployed version matches before testing an environment.

The existing group synchronization guard remains in place. This phase is not complete and no automatic revocation or combined-rights device push has been added. Before enabling those operations, implement coverage of all membership and configuration change paths, durable workers, revision checks, idempotency, retry/backoff and operator visibility; define ownership of manually configured device rights; read the actual device state, preserve unmanaged rights, write one complete effective state, and verify it by reading back. Cover offline failures, concurrent membership changes, same-door conflicts and remaining group access with integration and representative hardware tests. Coordinate with the existing offboarding pipeline rather than replacing it.

The operation table requires migration `1797900040000-CreateAccessReconciliationOperations`. Direct and unlinked capture additionally requires `1797900090000-AllowDirectAccessReconciliation` and `1797900091000-CaptureDirectAccessChanges`; deploy the compatible code and schema together. Rollback refuses to remove direct or unresolved history. Back up first, coordinate older writers and verify the earlier phase 0 PIN migration separately. Records do not establish that PINs, cards, fingerprints, credentials, or door rights are present on the device.
